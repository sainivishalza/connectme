# Architecture decisions (deviations from the original spec)

Source specs: `prompts/1_full_spec.txt` (authoritative), `prompts/0_prd_and_prompts.txt`.

1. **profiles.mode** has 3 values `open | incognito | hotel`, enforced by CHECK constraint.
2. **PostGIS + pgcrypto** enabled in migration 000; compose uses `postgis/postgis`.
3. **Extra tables** (swipes, blocks, reports, coin_ledger, gift_catalog, hotel_board_posts, refresh/verification/reset tokens, group_invites, reveal_consents) added in migrations 002+.
4. **Chat messages live in MongoDB only**; the Postgres `messages` table from the spec is dropped.
5. **Hotel auto-delete is keyed by `checkin_id`** carried on matches, board posts and Mongo messages; one idempotent job purges everything.
6. **Never-checked-out users** get `auto_delete_at` from a max-stay fallback.
7. **E2E = client-side libsignal (1:1 only in Phase 1)**; server stores ciphertext only. Moderation runs on reports and uploads, not on the chat stream.
8. **Node realtime service lives in `realtime/`**; Go serves REST only.
9. **Rate limits are per-route**: per-user for swipes, per-IP for auth.
10. **Refresh tokens use families**; reuse of a rotated token revokes the family.
11. **Config fails fast** on weak/placeholder JWT secret.
12. **Age gate uses `date_of_birth`**, server-side, 18+.
13. **Exact coordinates never leave the server**; distances are bucketed.
14. **One `PublicProfile` projection** is the only way profiles are serialized to other users.
15. **MVP drops Elasticsearch, Kafka, Kubernetes**; nearby search uses PostGIS.
16. **CSAM and ID/liveness sit behind interfaces** with dev stubs; real vendors are launch blockers.
17. **Stripe webhooks are signature-verified and idempotent** (unique `stripe_event_id`).
18. **Moderation module** (report/block + AI) is part of Steps 4 and 9.
19. **Live streaming (LiveKit) and Phase 2/3 are deferred.**

## Added in Step 5 (chat)

20. **Server stores ciphertext only.** The Go API validates the *envelope* (base64, size, type, burn timer), never content. There is no plaintext, content or text field in MongoDB.
21. **Signal key directory.** `key_bundles` + `one_time_prekeys` hold public keys only. A bundle is fetchable solely by the other participant of an active match; each one-time prekey is consumed atomically and used once. Phase 1 is single-device and 1:1.
22. **Burn-after-reading** starts when the *recipient* reads (`burn_at = read_at + burn_after_s`); the sender reading their own messages does not start it. A once-a-minute job deletes expired messages and their attachments; expired messages are also filtered out of reads immediately.
23. **Attachments are client-encrypted blobs** (`/chat/matches/{id}/media`, 8 MB). Because they are ciphertext the server cannot CSAM-scan them: that check must run on the sender's device *before* encryption, and abuse is handled through reports carrying decrypted evidence. Profile photos (not E2E) are scanned server-side. **This is a known tension between spec items "E2E for all chats" and "CSAM hash matching before ANY media publish"; legal review is required.**
24. **Deleting a conversation is for both sides** (ciphertext cannot be deleted "for one participant").
25. **Retention:** hotel purge removes messages and attachments by `checkin_id`; a sweeper removes conversations of matches that are no longer active (unmatch, block, ban).
26. **The Node relay is stateless and untrusted.** It authenticates the JWT, then forwards every action to the Go API with the caller's own token, so authorization has one source of truth. Membership is re-checked every 20 s so unmatch/block cuts a live socket off. Per-user message limit is 30/min across devices.
27. **Gifts in chat** are rejected until payments (Step 7), because they must debit coins.

## Added in Step 8 (Flutter app)

28. **State management is Riverpod; navigation is GoRouter** with a pure, unit-tested redirect rule (`redirectFor`). Tabs: Discover, Hotel, Groups, Chats, Profile, each with its own stack.
29. **Tokens live in the platform keystore** (`flutter_secure_storage`). The API client refreshes once, single-flight, and retries on a *separate* Dio so a second 401 cannot deadlock the queued interceptor (found by test).
30. **E2E is implemented client-side with `libsignal_protocol_dart`**: persistent identity/session/pre-key/sender-key stores in the keystore, namespaced by user id. 1:1 uses pairwise sessions named by conversation id; groups use sender keys distributed through the server's opaque envelope mailbox.
31. **Decrypted messages are cached on device.** A Signal message key works once, and sent messages are encrypted for the recipient, so history is only readable from the local cache. Consequence: **uninstalling the app loses chat history by design.** There is no server-side backup.
32. **Identity changes are not trusted silently** (trust on first use; a changed key fails decryption until the user resets that contact). A user-facing safety-number / "contact reinstalled" UI is not built yet.
33. **Photos are fetched through the authenticated API** (never a bare URL), so visibility rules apply to every byte.
34. **Checkout opens the system browser** with a server-created Stripe session. Apple/Google in-app-purchase rules for digital goods are an unresolved launch blocker (see Step 7 notes).
35. **Voice notes, voice/video calls, and live streaming UI are not in this build** (spec F1.7 voice notes and F1.8 calls need WebRTC/LiveKit; deferred with live streaming).
36. **No Android APK / iOS build was produced on the dev machine** (Android SDK command-line tools and a Mac are missing). Verification: `flutter analyze` clean, 59 tests, and a full `flutter build web --release` compile.

## Added in Step 9 (AI service)

37. **The AI service is an enhancement, never a dependency.** Every call has a short timeout; five consecutive failures open a circuit breaker for 30 s; moderation **fails open** (the action proceeds and is logged) and scoring simply leaves a match unscored. Safety rests on reports, blocks and human review, with AI screening as an extra layer.
38. **Internal only, shared-secret authenticated** (`X-Internal-Key`, constant-time compare). With no key configured the service refuses all requests unless `AI_ALLOW_NO_KEY=1`. It is never exposed publicly and never logs payloads.
39. **Minimal inputs.** Scoring receives tags, age, active hours and message *counts*. Moderation receives only public text. No names, refs, coordinates or chat content (chats are E2E and never leave the device unencrypted).
40. **Scoring weights** are interests 40 / age 20 / schedule 20 / conversation 20. Missing signals are neutral (sparse profiles are not punished) and are never offered as "reasons". Age-derived reasons are dropped for incognito/hotel matches so approximate age cannot leak before a reveal.
41. **Text moderation is rules-based and conservative:** it blocks clear minors, threats, commercial sex, scams and link spam; sends ambiguous cases (profanity, off-platform contact, contact details) to a human queue. It is not a classifier; production should add vendor lexicons (`MODERATION_EXTRA_BLOCKLIST`) and a model behind the same interface.
42. **Image moderation does NOT detect nudity or violence without a model.** It validates structure, checks an operator hash blocklist, and returns `screened_by_model=false` so this is never mistaken for full screening. CSAM detection still requires a licensed hash vendor (PhotoDNA/NCMEC): a launch blocker.
43. **Wingman is deterministic and template-based** (no LLM key needed); venue ideas are kinds of places, not businesses, since no location is shared with the service.

## Added with the moderator dashboard and metrics

44. **The dashboard is a thin client of the existing API.** It is embedded in the binary, has no build step or dependencies, writes untrusted text only through `textContent`, and ships a CSP of `default-src 'none'; script-src 'self'`. Every permission check stays server-side.
45. **Staff see less than users' own data.** The staff user view omits email, phone, date of birth and location. Photos are viewable only while an open report concerns that user, and each view is audited.
46. **Every staff read of a user and every action is written to an append-only audit log** (DB trigger forbids delete and rewrite). Bans require a 5-300 character reason, respect role hierarchy, and revoke sessions. Reading the audit log is itself logged and admin-only.
47. **Metrics are never on the public listener.** `/metrics` lives on `METRICS_ADDR`; labels use route patterns (never raw paths or IDs) so cardinality is bounded.
48. **CI runs all four suites on every push** (`.github/workflows/ci.yml`: Go with real PostGIS/Redis/Mongo services, pytest, node, flutter analyze+test).
49. **Kubernetes manifests are deny-by-default.** The AI service accepts traffic only from the API; the API's metrics port only from the `monitoring` namespace; media needs a ReadWriteMany volume until an object store replaces local disk.

## Added with live streaming (backend)

50. **Live streaming is a thin control plane over LiveKit.** The API decides who may host or watch and mints short-lived (2 h) LiveKit tokens locally signed with the API secret, scoped to one room and one identity (viewers can only subscribe). It is mounted only when `LIVEKIT_URL` is set.
51. **Only verified, non-banned members in Open mode can host.** Incognito and hotel members cannot broadcast, so a stream can never expose an identity they chose to hide. One live room per host; rooms auto-end after 6 h or when the host is banned.
52. **Blocks apply in both directions** to listing, joining and gifting, and joins to ended or banned-host rooms return 410.
53. **Gifts are idempotent and conservation-checked.** Charge, 70% host credit and 30% platform share happen in one transaction keyed by `(from_user, request_id)`; a DB check enforces host + platform = price. Self-gifting is refused.
54. **The Flutter live screens depend only on a small `LiveMedia` interface**; `livekit_client` is confined to `media_session.dart` so widget tests run without WebRTC. Leaving the broadcast screen or failing to start the camera ends the room, so no orphaned live room remains.
55. **In-stream chat and gift announcements are server events, polled every 2 s** (`GET /live/rooms/{id}/events?after=`), not LiveKit data messages, so every line passes block filtering, text screening and rate limits (40 messages/min). Senders not in Open mode appear as "Someone". Events are public and not E2E encrypted; they are deleted with the room 24 h after it ends. Polling is simple and bounded; a push channel is a scaling follow-up.
55a. **Staff can end a stream** (`POST /moderation/live/{id}/end`, mandatory reason, audited as `end_stream`) from the dashboard's Live tab, and banning a host ends their rooms immediately and closes the media room.
56. **Android/iOS permission declarations were missing entirely** (internet, location, camera, microphone, photos) and are now in the manifests; they are untested without a device build.
57. **LiveKit integration is verified against the real server, opt-in.** `internal/live/livekit_real_test.go` (set `TEST_LIVEKIT_URL`/`TEST_LIVEKIT_SECRET`; CI runs it with a LiveKit service container) checks that the signalling endpoint upgrades with our viewer token, rejects a corrupted one, and that closing a room deletes it.
58. **Hosts moderate their own chat.** `POST /live/rooms/{id}/moderate` (host only, live rooms only) mutes a viewer (can watch, cannot chat) or kicks them (cannot rejoin, and the media server is told to disconnect them). A mute never downgrades a kick. Both are scoped to the room and vanish with it; platform-wide action remains with staff.
59. **Money paths are race-tested.** Concurrent gifts from one wallet (live, payments) and boosts never overdraw and never deadlock; a repeated `request_id` charges once; viewer payments equal host share plus platform share. The test found a real deadlock in live gifts (the foreign-key share lock from the claim insert was taken before the wallet's `FOR UPDATE`); the payer's row is now locked first. Rule for future spend paths: lock the payer's `users` row before inserting anything that references it.
60. **Rate limiting fails closed except for cheap authenticated reads.** Security-relevant limiters (login, register, writes, payments, gifts) return 503 when Redis is down so limits can't be bypassed; limiters whose name ends in `read`, `list` or `events` let the request through (access tokens are stateless, so reads still authenticate) and increment `ratelimit_fail_open`. New read-only routes should follow the naming convention; anything that changes state must not.
61. **Dependency scanning is part of CI.** The first `govulncheck` run found that user-uploaded photos were decoded by a 2019 `golang.org/x/image` (9 reachable advisories, e.g. a crafted-TIFF denial of service) pulled in indirectly by the imaging library; it is now v0.47.0 and the scan reports none reachable. Indirect dependencies are exactly where this hides, so the scan stays in CI.
62. **Email goes out through a generic SMTP client**, asynchronously via a bounded queue (a slow relay cannot slow sign-up, and response time does not reveal whether an address already has an account). Recipients are parsed and CR/LF-checked against header injection, credentials are refused without TLS, bodies are never logged, and production refuses to start without `SMTP_HOST`/`SMTP_FROM` or with plaintext allowed.
63. **Media storage is pluggable.** `users.MediaStore` has a local-disk implementation and an S3-compatible one (`minio-go`, keys `photos/<uuid>.jpg` and `chat/<uuid>.jpg`, ids validated as UUIDs so callers cannot choose keys, optional SSE). A bad S3 configuration stops startup instead of silently falling back to disk. Objects are never exposed by URL; downloads go through the API's authorization checks. The integration harness can run the entire suite on S3 via `TEST_S3_ENDPOINT`.
64. **Account security actions.** `POST /auth/change-password` (current password required, per-user limit of 5/hour so it cannot serve as a password-guessing oracle, answers 403 not 401 on a wrong current password so clients don't treat it as an expired session) revokes every other session and returns a fresh pair for the calling device; `POST /auth/logout-all` revokes every refresh token. Already-issued access tokens used to stay valid for up to their 15-minute lifetime; decision 119 now voids them at once.
65. **Rate limiting is audited at runtime, not only by regex.** Limiters now send `X-RateLimit-Limit`, and a test requests every route of the live router and fails if one answers without passing a limiter, so wrapped registrations or helper functions can't hide an unlimited route. The header also lets clients show limits. Exempt: `/healthz`, `/readyz`, and the Stripe webhook (signature-authenticated).
66. **Provider retries are limited.** Riverpod 3 retries every failed provider up to 10 times while showing "loading", which made a plain 404/403 look like an endless spinner (found by trying the app in a real browser). `appRetry` (passed to `ProviderScope.retry`) retries only network failures and 5xx, at most twice (1 s, 2 s); client errors surface immediately. Covered by a widget test that fails without the policy.
67. **Visual identity: "the hour you choose to be seen".** Each visibility mode is a time of day with its own light: Open is Daylight (peach to raspberry), Incognito is Dusk (indigo to periwinkle), Hotel is Lamplight (gold to amber). The interface itself stays quiet (cool porcelain and ink, no cream, no purple-gradient wash); colour with meaning is reserved for the modes: the mode panel on Profile, avatar rings, the veil behind anonymous people, and the Like button. Tokens live in `lib/core/theme/tokens.dart`, the theme in `app_theme.dart`.
68. **Type: Gloock (serif) for titles and names, Figtree for UI, both bundled.** Fonts are shipped as assets under the SIL Open Font License (`assets/fonts/OFL-*.txt`) rather than fetched from a font CDN, because a privacy-first app should not tell a third party that each user opened it. Sentence case throughout; no all-caps labels.
69. **Shape follows importance:** hero surfaces radius 28, cards 20, controls 14, pills fully round, so shape signals what you are touching. The primary action is an ink pill; navigation is a floating ink pill. On screens wider than 760 px the app is a 460 px column on a soft field of the three lights (`AmbientFrame`), so the web version reads as a device, not a stretched phone layout.
70. **Anonymous people are shown behind a veil, not a grey placeholder:** their mode's light with a closed-eye mark and the line "Face hidden until you both reveal". The server contract is unchanged: the card still never receives a name or photo for anonymous profiles, and tests assert it.
71. **Anonymous random matching (F1.6) reuses the match and chat machinery.** A pairing is a row in `matches` with `origin='random'`, mode forced to incognito and a 10-minute `expires_at`, so end-to-end encryption, reveal consent, block, report, erasure and retention all apply unchanged. If both people choose Keep chatting before time runs out, `expires_at` is cleared and it is an ordinary incognito match; otherwise it is ended (the chat is closed at once by an expiry predicate in chat access and the matches list, and a 15-second job marks it rejected so the retention sweeper purges the messages). A pair is never matched twice, and never matched with someone they blocked or were already matched with.
72. **Queue and fairness.** Waiting people live in `random_waiting` (dropped after 90 s or when they leave the screen); pairing runs under a Postgres advisory lock so two joiners can never get the same partner, preferring the candidate with the most shared tags, then the longest wait. Serialised pairing is fine at modest scale; a busy deployment should shard the queue.
73. **Abuse controls for anonymous strangers:** verified, non-banned members only; 20 joins per hour; peers appear only as an anonymous incognito card (no name, photo, age); leave, block and report work as in any chat. Because chats are end-to-end encrypted, nothing in them is scanned: reports carry the reporter's own evidence. Running this feature publicly needs moderator capacity and a clear policy first.
74. **Voice notes (F1.7) ride the existing encrypted attachment path.** A clip is recorded (AAC where supported, Opus otherwise; mono, 48 kbps, at most 2 minutes), encrypted with a fresh key like an image, uploaded as an opaque blob, and sent as a `voice` message whose key, MIME type and duration live inside the Signal ciphertext, so the server sees only an encrypted blob and a type. Audio is downloaded and decrypted only when played. The recorder and player sit behind small interfaces (`voice_io.dart`) so screens and tests never touch the microphone; the real devices need a physical-device check (microphone permission, Safari's recording format).
75. **Voice and video calls (F1.8) are one-to-one over LiveKit with a small server-side state machine** (`ringing`, `active`, `ended`, `declined`, `missed`; 45 s ring time, 2 h cap). The server decides who may call; media never touches it. Each side gets a token for one room (`call-<id>`) for at most two hours. Mounted only when `LIVEKIT_URL` is set, like live streaming.
76. **Calls reveal faces and voices, so they are gated.** The match must be active with nobody blocked or banned; an anonymous random chat can be called only after both people kept it; a video call in an incognito or hotel match needs mutual reveal first (voice only does not). One call at a time per person, enforced under a row lock. A ban hangs up the person's calls and closes the room.
77. **Incoming calls are found by polling (every 3 s while the app is open), and now also pushed.** The server sends a high-priority "Incoming call" notification (decision 106-110), but delivery needs a Firebase project, the Firebase plugin in the app and a physical device, so until those exist a call still cannot wake a closed app: polling is the fallback. Polling stops for good if the server answers 404 (calls disabled).
78. **Voice intro (F2.12) follows the photo visibility rule exactly.** A voice identifies a person, so the clip is served only to someone who may see the owner's full profile (`ResolveVisibility == VisFull`): never for an incognito or hotel profile, never before mutual reveal in an anonymous match, never to a blocked or banned person. For anyone else the answer is "not found", so its existence is not even confirmable. The format is decided from the file's own header (MP4/AAC, WebM, Ogg), never from the client's claim; clips are capped at 30 s and 1 MiB, replaced or deleted by their owner, and deleted on account erasure. Audio cannot be screened by the current AI service, so reports are the safeguard.
79. **Social games (F2.5) split by sensitivity.** Prompts (truth, dare, icebreaker) are a curated, adult-appropriate bank in code with a test that rejects sexual, alcohol, personal-data or risky content, and are sent into the chat as ordinary end-to-end encrypted messages. The couple quiz stores multiple-choice answers per match on the server so two devices can be compared, and reveals the other person's choices only when both have finished; answers are deleted with the match or either account. Games work in any active match, including anonymous random chats (answers identify nobody), and end when the chat ends.
80. **Posts are one engine with four kinds (F2.7, F2.9, F2.10, F2.6).** Moments, Little Universe, missed connections and group posts share one table, one query (`social.query`, fixed parameterised SQL) and one visibility function (`canSee`), so a rule cannot be fixed in one feed and forgotten in another. Lifetimes: moment 24 h, universe 48 h, missed connection 72 h, group post 14 days; a 5-minute job deletes expired posts. Per-kind daily limits and text screening apply on write.
81. **Each kind has its own identity rule.** Moments show the author the way their mode allows (an Incognito author is shown as an anonymous card, never a name or photo). Little Universe shows a made-up nickname only; the author's own view is the only place both are linked, and the feed never returns an author id. Missed connections are visible only to people checked in at the same venue, show no distance and no author, and are bound to the check-in so they vanish with the stay.
82. **"That's me" on a missed connection is a consent handshake.** Anyone at the venue can say it; the poster sees the claimants as anonymous cards and decides. Accepting creates a hotel-origin match bound to the check-in (24 h retention applies); declining tells the claimant nothing beyond "not now". Nobody learns who read the post.
83. **Nearby groups (F2.6) are interest groups (within about 25 km, up to 3 owned per person) and automatic hotel groups.** A hotel group exists while there is a stay at that hotel; membership is bound to the check-in with cascade delete, you cannot leave mid-stay, and checking out removes you. Posts are members-only (visible and reportable only to members); the owner can remove posts, and an owner who leaves hands the group to the longest-standing member or deletes it when empty.
84. **Audio rooms (F2.4) are LiveKit voice rooms with a stage.** The host starts a room (one per host), listeners join with subscribe-only tokens, raise a hand, and the host promotes up to 7 speakers. The LiveKit identity is a per-room member id, never the user id. Promotion updates LiveKit's permission (best effort) and the member rejoins for a token that carries it; the server, not the client, decides who can publish. A host leaving or being banned ends the room; members who stop polling for 90 s are dropped; kicked people cannot rejoin.
85. **Audio-room names follow a stricter rule than streams.** A real display name is shown only in a named room and only for Open-mode members; everyone else, including every Incognito member, gets a generated alias. An Incognito host can only open an anonymous lounge, and Hotel-mode members cannot take part at all (a voice identifies a person).
86. **Masked Truth (F2.8) is the anonymous random pairing played as truth or dare**, not a new system: the same queue, expiry, Keep-only-if-both and encrypted chat, with a `style` column that keeps the truth queue apart and tells the client to open the game sheet. Prompts come from the curated bank (decision 79); no turn state is stored.
87. **Short videos (F2.3) and reels (F2.11) are off unless `ENABLE_VIDEO=true`.** There is no video-aware abuse or CSAM scanner, so enabling them in production is a launch blocker until one is wired in. Only Open-mode verified members can post a short; a reel is allowed in any mode but is served exactly when the owner's photos are (`users.SeesFull`), so anonymous profiles never expose one and do not even advertise its length (`reel_s` is attached only to non-anonymous profiles).
88. **Video files are validated from their bytes, not the client's claim.** Only MP4/QuickTime is accepted (`ftyp` header), the length comes from the `moov/mvhd` box (30 s at most; files without a readable header are refused), 12 MB at most, 5 shorts per day. Files are stored in their own media namespace and are served only through 10-minute HMAC-signed URLs (`/videos/file/{id}?exp=&sig=`) minted after the same access check, because browsers and native players cannot send an Authorization header; the route supports range requests so players can seek. Deleted, replaced, removed or banned-owner videos stop serving at once.
89. **Video moderation and erasure.** Viewers can report any clip they may watch (reason code, evidence is the clip id and caption), staff remove a clip with a mandatory reason (`POST /moderation/videos/{id}/remove`, audited as `remove_video`), and account erasure deletes the files as well as the rows.
90. **The Flutter video player sits behind `videoViewBuilderProvider`** so widget tests never need a codec; `video_player` is confined to `widgets/video_view.dart`. The feed is a vertical pager that plays only the visible page.
91. **Lists of people carry optional media hints, never media.** `voice_intro_s` and `reel_s` (seconds) are added only to non-anonymous profiles; the media is fetched on demand and re-checked by the server. A test fails if an anonymous profile ever carries either.
92. **Forums (F3.1) have two kinds of identity and no stored aliases.** Boards are seeded (dating advice, first dates, travel tips, solo travel) and admins add city boards (`POST /forums/boards`, admin only). A post shows the author's display name only while they are in Open mode at the moment it is read; anyone else gets an alias derived from SHA-256 of (thread, user, server secret): stable inside one thread, different in another, never stored, and never linked to a ref. Going Incognito later therefore hides earlier posts too. Limits: 10 threads and 60 replies per person per day; text screened like other public text; blocks hide posts in both directions; staff remove a thread or reply with a mandatory reason, audited as `remove_forum_post`. A slug that is not `[a-z0-9-]{2,40}` is "not found" before it reaches the database (the hostile-input audit found a NUL byte turning into a 500).
93. **Mood-based hotel discovery (F3.2) is a per-stay setting.** A guest picks one of three moods (on a business trip, looking for company, happy to show you around) on their check-in; it is cleared with the stay, filters the hotel feed (`?mood=`), shows as a chip on hotel cards and as counts to other guests. Hotel cards stay anonymous: the mood is the only extra thing they carry.
94. **Chapter-based profiles (F3.3) follow the photo rule.** Up to five chapters (title 3-60, text 10-600 characters), replaced as a set, readable only through `users.SeesFull`, "not found" otherwise, and advertised in lists only as a count on non-anonymous profiles (`chapters`). They are personal stories, so they are screened as bio text.
95. **Partners, events and bookings (F3.5, F3.6, F3.7) are one module, `partners`.** Admins add hotels, restaurants and activity providers (location, commission 0-30%) and schedule events for them. Members see events within about 50 km, plus mixers of the hotel they are checked in at. A mixer is always limited to that hotel's guests, and its RSVPs hang off the stay so they are deleted with it. Attendance is a count, never a list of people.
96. **Tickets are coins; bookings are requests.** Paid events charge through the existing coin ledger (idempotent by a per-RSVP reference, so leaving and re-joining is charged and refunded on its own), capacity is enforced under a row lock, leaving before the start refunds, and cancelling an event refunds everyone. A booking is a request (party size, time within 120 days, a note) that staff confirm or decline on the partner's behalf; confirming records the agreed amount, completing fixes the platform's commission (`amount x commission_bps / 10000`), and `/partners/{id}/report` totals what is owed for settlement outside the app. Collecting the money is covered by decisions 111-114; paying partners out (Stripe Connect or invoicing) is still a launch task.
97. **Partner administration was admin-only at first.** Admins still create partners and link managers; day-to-day running moved to the partner portal (decisions 115-118).
98. **F3.4 (AI Wingman as a full agent) was deferred, then built in decisions 124-127.** It reads only an activity, a group size and interest tags, never profiles or chat, which is what keeps the prompt-injection surface small.
99. **Video scanning is an interface with a fail-closed default (`videos.Scanner`).** Every clip is scanned after validation and before it is stored: `allow` goes live, `flag` is stored but held for a moderator, `block` is refused with "This video is not allowed" and queued as an automatic report against the uploader, and a scanner that errors, times out or answers nonsense holds the clip instead of publishing it unreviewed. Two implementations ship: a stub that allows everything (development) and an HTTP scanner that posts the raw clip with a bearer key and expects `{"action","reason"}` (any provider can sit behind a small adapter). The provider itself, and its accuracy, are still the operator's to choose and verify; this change makes it pluggable and enforces what happens with its answers.
100. **Held clips are invisible to everyone but their owner and staff.** The feed, likes, reports, tickets, reels and the `reel_s` hint all require `status='live'`; the owner sees their own clip marked "under review". A held reel replaces the old one immediately (the old file is deleted on replace), so a profile has no reel until approval.
101. **Production rule for videos changed from "never" to "needs a real scanner".** `ENABLE_VIDEO=true` in production now requires `VIDEO_SCANNER=http` with an https URL and key; `stub` or a missing URL/key stops startup. This is a configuration check, not proof that the provider is good.
102. **One staff queue for everything waiting on a human.** `GET /moderation/queue` merges open reports (user reports and automatic flags) and held videos, oldest first so nothing starves; the dashboard opens on it and shows a "Videos held" count. A moderator can watch a held clip (a signed 10-minute link, audited as `view_video` before the link is returned), approve it (`approve_video`, reviewer recorded) or remove it with a reason (`remove_video`). Watching personal content by staff is itself an audited action, like viewing a photo. The dashboard's CSP gained `media-src 'self'` only.
103. **Feeds that show a card per row must use `users.Cards`, never `users.Card` in a loop.** A load test of the Phase 2/3 read paths (80 concurrent members, 4000 posts, 1500 videos, 400 forum threads, 150 partners) showed the moments feed taking 7.7 s at the median because each of its 30 rows triggered about six queries. `Cards` returns the same projection for many people in a constant number of queries; a test compares it with `Card` field by field for self, open, anonymous, matched, revealed, blocked, banned and unverified people, with and without a hotel name, so the batch form cannot drift from the privacy rules. Posts, matches and the hotel feed use it.
104. **The block check is two `NOT EXISTS`, not one with `OR`.** The OR form made Postgres scan the whole `blocks` table once per candidate row (visible in `EXPLAIN` as a sequential scan inside a nested loop); two independent lookups use the `(blocker_id, blocked_id)` primary key. The helper `users.notBlocked` is the single definition, so every feed gained the fix; semantics are unchanged and the visibility tests cover it.
105. **Post locations are already snapped when stored**, so the feed query no longer re-snaps each post (only the viewer's position, once, via a lateral join). Together with 103 and 104 the combined feed load went from 67 s to under 20 s for the same work. `TestFeedsUnderLoad` (opt in with `LOAD=1`, `KEEP=1` leaves the data for `EXPLAIN`) fails a build whose p95 on any feed exceeds 2 s.
106. **Push notifications are generic by construction.** A notification reaches a lock screen and passes through Google's and Apple's servers, so it says only "You have a new message / match", "Incoming call" or "Your booking was updated", titled "ConnectMe". The data attached is the kind and one opaque id (a match, call or booking id). No names, no photos, no message text, no venue: chat is end-to-end encrypted and many matches are anonymous, so nothing may leak through this channel. A test asserts the payload contains only those fields and none of the sender's identity.
107. **Delivery is asynchronous, collapsed and preference-aware.** Features call a non-blocking `push.Notifier`; a bounded queue (drops, and counts, rather than slowing a request) feeds four workers. A burst in one chat is one notification (a Redis `SETNX` window: five minutes for messages, 20 s for calls, one minute otherwise; a Redis failure fails open, since a duplicate beats a missed call). Members switch kinds on or off (`/push/prefs`); banned or unverified accounts receive nothing; the sender is never notified of their own message; a liking alone is silent and only a completed match notifies the person who liked first.
108. **The provider sits behind `push.Provider`.** `stub` (default: records in memory, used by tests and development) and `fcm` (Firebase Cloud Messaging HTTP v1, which also reaches iOS through APNs). The FCM client signs a service-account JWT (RS256), exchanges it for a short-lived OAuth token and caches it, and sets high priority and a 45 s lifetime for calls and a collapse key per conversation. Only an explicit `UNREGISTERED`/404 deletes a device token: a 400 may be our own payload bug and must never wipe every device, and an outage never deletes anything. A bad key stops startup instead of silently dropping every notification.
109. **Tokens follow people, not phones.** A token is unique and belongs to whoever registered it last (a shared phone stops notifying the previous account); ten devices at most; unused tokens are removed after 90 days; signing out unregisters the device, and "sign out everywhere" and a password change delete every device on the server, so a phone that was signed out remotely cannot keep receiving notifications. The device that stays signed in registers again.
110. **The app is built without Firebase, on purpose.** `PushTokenSource` is the only place the app touches a push plugin; the default `NoPushTokenSource` reports "not available" and the rest (registration, preferences, tap routing) is complete and tested with a fake. Adding `firebase_core`/`firebase_messaging` and the platform config files needs a Firebase project and a physical device, neither of which exist here, and would break the web build without them. The app never prompts for permission by itself: only the "Turn on notifications" button in Settings does, and registration afterwards is silent.
111. **Booking payments reuse the existing Checkout and webhook path, and the database decides the price.** A member pays a *confirmed* booking through a Stripe Checkout Session whose amount is the one staff recorded at confirmation; the client sends nothing but the booking id. The webhook marks the booking paid only when the booking belongs to the named member, the paid amount equals the recorded amount and the currency matches; anything else is logged as "refund needed" and changes nothing (the money then needs a manual refund). Replays and a second session for the same booking do not double count (event ids, and `payment_status` is checked under a row lock). Stripe's 50-cent floor is enforced before calling Stripe.
112. **Once paid, the price is frozen.** Staff can still complete the booking (which fixes the commission) but cannot change the amount of a paid booking.
113. **Refunds are requested by an admin and recorded when Stripe confirms.** `POST /payments/bookings/{id}/refund` (admin) asks Stripe for a full refund; the booking becomes `refunded` only when the `charge.refunded` webhook arrives, so the app never claims a refund that did not happen. A member can cancel a paid booking, which does not refund it automatically: the partner report counts it under `refunds_due` so staff act on it deliberately (the venue's own cancellation policy is not something the platform can decide).
114. **Settlement is reported, not performed.** `/partners/{id}/report` now shows what was collected through the app, the commission on completed bookings, the amount owed to the partner (collected on completed bookings minus commission) and refunds due. Paying partners out (Stripe Connect or bank transfer) is still done outside the app against that report. Request shapes for checkout and refunds are validated against Stripe's official OpenAPI spec with `stripe-mock` (opt-in test).
115. **The partner portal uses ordinary member accounts linked to a partner, not a new role.** An admin links a verified member to a partner by email (`partner_managers`; the response and the list show a public ref and display name, never an email). A manager's access is proven on every request against that link and ends the moment an admin removes it or the member is banned, so there is no standing partner credential to leak and no new login system to secure. Managers get `/partners/manage/...` and nothing else: no admin routes, no refunds, no other partner's data (other partners' ids answer "not found").
116. **A venue sees who is coming, not who they are.** Managers see a booking's guest as the member's display name only when that member is in Open mode, and as "Guest XXXX" (the booking's short code) otherwise; never a public ref, email, photo or mode. The member's own booking list never carries a guest label. A guest in Incognito or Hotel mode has not agreed to be named by booking, and the code lets the venue and the guest still recognise each other at the door.
117. **Managers can run what they own and no more.** Schedule events (20 upcoming at most per partner), cancel them (which refunds every ticket), confirm or decline bookings and complete them, and read the earnings report. A manager can set a booking's price when confirming; that price is what the guest is charged (decisions 111-113) and what the commission is computed on, so a rogue manager can only affect their own venue's revenue.
118. **The portal is a static page with the dashboard's CSP** (`/partner/`, embedded in the binary): no inline script or style, no third-party origins, `media-src` and framing denied, and all member text goes in through `textContent`. A test fails if the script ever uses `innerHTML`, `eval` or similar, and serves only the three known assets. Everything it does is an authenticated `/partners/manage` call, so server-side scoping applies exactly as for any other client.
119. **Revoking a session now voids its access tokens at once.** Access tokens are stateless and used to stay valid for their whole life (up to 15 minutes) after a ban, "sign out everywhere", a password change or reset, or an erasure: a banned or locked-out person kept acting. `RevokeAllForUser` now also records a cutoff time in Redis (`ucut:<user>`, kept two hours, longer than any access token), and the authentication middleware refuses a token issued before it. A token issued in the same second as the revocation survives (tokens are dated to the second), so a fresh sign-in right after a password change works. If Redis cannot be read the middleware fails open and counts `session_cutoff_unavailable`, the same trade-off as the read rate limiters. Decision 64's "up to 15 minutes" no longer holds for these events.
120. **The role in an access token is trusted until it is revoked.** Demoting a moderator in the database does not take effect until their sessions are revoked; `POST /moderation/users/{ref}/revoke-sessions` (admin only, reason required, audited as `revoke_sessions`) does that. The runbook says to use it after any direct role change.
121. **Chat now shows when the other person's security key changed.** The Signal layer already refused a changed identity key (tested), but the app only showed "Couldn't decrypt this message" with no explanation and no way forward. The chat now shows a "Their security key changed" banner, refuses to send until it is reviewed, and "Verify security" shows a 60-digit safety number (both identity keys, hashed and combined in a fixed order so both people see the same digits) to compare in person or over another channel, with a "Trust the new key" action that drops the old session. The number format is ConnectMe's own, not Signal's, so it cannot be compared with another app. One-to-one chats only; group chats have no safety number yet.
122. **A matched person can no longer drain someone's one-time prekeys.** Each requester gets one one-time prekey per conversation per day (`prekey_fetches`); a repeat fetch still gets the identity and signed prekey, and X3DH works without a one-time prekey. Previously 60 fetches an hour from any match could exhaust the supply and weaken the first message of every later chat.
123. **The realtime relay has a per-user budget for every event** (240 a minute across all of a user's devices, on top of the 30 messages a minute), so a socket cannot flood a peer with typing events or hammer the API through the relay. CORS preflight now allows `PUT`, which several routes use: without it a browser app on a different origin from the API could not call them.
124. **The AI Wingman (F3.4) is a language-model planner with a deterministic net underneath.** With `WINGMAN_PROVIDER=llm` and an `ANTHROPIC_API_KEY`, the AI service asks the model for venue *kinds*, icebreakers and a 3-5 step outing plan for a group date; on any problem it serves the template suggestions that existed before (`source: "ai"` instead of `"llm"`), so the feature never fails and never depends on the provider being up. The model sits behind a one-method interface (`wingman/llm.py`), so another provider is a small class, and the default model is configurable (`WINGMAN_MODEL`).
125. **Treat both ends of the model as untrusted.** Input: the model sees only an activity, a group size and interest tags, no names, locations, bios or chat. Tags are member-typed, so they are cleaned to short plain words (three words at most, a restricted alphabet, no instruction-like words, moderation-screened) and placed in a JSON block the system prompt declares to be data, not instructions. Output: the answer must parse as the exact expected JSON shape, and every string must be 8-140 characters with no links, handles, emails, long digit runs or markup and must pass the same text moderation as profile text; **one** bad string rejects the whole answer. A model that is manipulated, wrong or compromised can therefore, at worst, produce suggestions that are bland or silly, not ones containing contact details or abuse.
126. **Cost and privacy limits.** Answers are cached for an hour per (activity, group size band, tags), the process makes at most `WINGMAN_LLM_RPM` (default 30) model calls a minute and falls back to templates beyond it, calls time out after 8 s, and prompts and answers are never logged (only the outcome). The Go API's timeout for the AI service rose from 3 s to 12 s to leave room for a model call, and it no longer trusts the service to name its own `source` (only `llm` is passed through).
127. **The app labels model-written ideas** ("Ideas written by an AI assistant... check details yourself before you go") and shows the outing plan as numbered steps when present. Venues stay generic kinds of places because the model is never given a location and cannot know real businesses; it could not be trusted to get opening hours or safety right if it did.
128. **Truth or Dare now has real turns.** One game per match (`td_games`): whose turn it is, whether they are choosing or answering, the drawn prompt and each player's skips. The starter goes first; the player whose turn it is picks truth or dare and gets a prompt from the curated bank; the other player sees the same prompt; "Done" or "Skip" (two skips each per game) passes the turn. Every transition is a single conditional update on (match, turn user, phase), so two taps or two devices cannot both act. The game is deleted with the match, and a block or an ended random chat closes it like any other game.
129. **Answers stay in the chat, not in the game.** The server stores only the prompt (public, curated), never what anyone said or did, so the game adds nothing about a person beyond "it was their turn". The prompt bank keeps the same content rules and test as decision 79.
130. **An idle player cannot stall the game.** After five minutes on the same turn the waiting player is offered "Take over", which makes it their turn to choose at no cost to either. Masked Truth (decision 86) now opens straight into this game for both anonymous players; the plain "draw a prompt" sheet is still there for sending a prompt into the chat. Group chats do not have it yet.
131. **The group-date logistics fee is 100 coins per person (about $1.80), charged when someone asks for the plan.** The PRD's "$1-5 per person for AI-coordinated logistics" is a per-person charge, so each member pays for themselves (`group_date_logistics`, one row per date and person); paying twice charges once (conditional insert plus an idempotent wallet reference). The plan (venue kinds, icebreakers, outing steps) is generated once per date, stored, and shared by everyone who pays, so the model is called at most once per date. It is generated *before* the charge, so a failed generation never costs coins. Not available once the date has started or was cancelled; cancelling a date refunds everyone who paid. Only members of either group can read or buy it; a stranger gets 404.
132. **Sponsored placements are a labelled card at the top of the Moments and Little Universe feeds, nowhere else.** Admins (hotel/partner management permission) create them with advertiser, headline, short text, optional https link, run window, optional place and radius, and optional impression cap. Silver and above never see one (the "no ads" perk, via entitlements). A member sees at most one every three minutes (Redis cap, so a refresh loop cannot inflate an advertiser's numbers), placements with a place reach only members whose snapped (0.01 degree) location is inside the radius, and the least-shown eligible placement goes first. Missed connections, chat and profiles never carry ads.
133. **Ads know nothing about people.** Only totals (impressions, clicks) are kept, never who saw or clicked; members never see counters. Links must be plain https to a named public host (no IP addresses, localhost, internal names or user:pass@ tricks), text passes the same screening as posts, and the app opens a link only through the click endpoint. An ad request that fails is silently dropped so it can never break the feed. There is no advertiser self-service or billing: placements are entered by staff (API only for now).
134. **Real LiveKit server tested locally.** `ops/dev/livekit-check` joins an audio room with the tokens our API issued (a speaker and a listener) through the open-source LiveKit server in Docker and proves audio frames reach the listener and that the listener's own publish attempt is refused (`TEST_LIVEKIT_URL`/`TEST_LIVEKIT_SECRET`, `internal/integration/livekit_real_test.go`, opt-in). Closing a room nobody ever joined no longer logs a failure (LiveKit creates rooms on first join, so DeleteRoom answers 404). Real phones, TURN/NAT traversal and load are still untested.
135. **A local nudity model, honestly scoped.** The AI service can load an ONNX image classifier (`NSFW_MODEL_PATH`; exported from the Apache-2.0 Falconsai/nsfw_image_detection by `tools/export_nsfw_onnx.py`). It scores "nudity" only; there is no violence model. Thresholds are the existing ones (0.85 block, 0.5 review). Set-but-broken path stops startup. Accuracy has not been measured on this app's real photos: expect false positives and misses, and keep the staff review queue.
136. **Video scanning by sampling frames.** `POST /moderate/video` (Bearer key, the contract the API's HTTP scanner already speaks) decodes the clip with PyAV, takes eight frames evenly across it, runs each through the same image checks (hash blocklist and nudity model), and answers with the strictest result: block, flag (to the review queue) or allow. Undecodable or over-long clips are blocked, and with no model configured the service answers 503 so the API holds the clip. It cannot see a short insertion between samples and does not analyse audio.
137. **F1.14 is delivered as "Ask Wingman for a reply", not as an AI inside the chat.** Group chats are end-to-end encrypted, so neither the server nor an AI can read them, and an AI member would need its own keys and could read everything every member sends. Instead, a member opens "Ask Wingman for a reply", sees their last eight text messages, ticks the ones to share (the latest three are pre-ticked), and taps "Get reply ideas". The app sends only those lines, each marked "me" or "other", with no names, ids or group data; the server checks the caller belongs to the group chat and relays them to the AI service, which returns three reply ideas.
138. **Shared lines are untrusted input and are never kept.** They are limited (1-8 lines, 300 characters, no control characters), screened by the content filter (a line that fails keeps the whole request away from the model, which then gets template replies), wrapped as data the model is told never to obey, not cached, not stored and not logged. Output goes through the same checks as the other Wingman answers (no links, handles, numbers, or moderation hits; one bad string rejects all three). 20 requests an hour per member. With the model off or failing, the member gets friendly generic replies. The sheet tells them other people's messages they tick are shared too; the group is not notified.
139. **Nearby search cost depends on how many people are in range, not on how many are online.** A load test with 5,000 people inside one 25 km circle showed `/users/nearby` taking 1-2 s and starving every other route (the first version scored every candidate with per-row sub-queries). It now (a) uses set-based joins for blocks, swipes and Platinum status, (b) fetches the wide columns (bio, photos) only for the returned page, and (c) searches small circles first (2, 5, 10, 25, 50 km up to the requested radius) and widens only when too few people are found. Widening is skipped, and the full radius searched, whenever anyone in range is boosted, because a boost outranks distance. Order, snapped distances and every exclusion are unchanged (tested against the old behaviour, including a far boosted person and paging). Result at 5,000 people in range: nearby p50 2,114 ms -> 27 ms at 100 users.
140. **Error tracking is a Sentry-compatible reporter that cannot expose people.** `SENTRY_DSN` (Sentry, GlitchTip or any envelope-API server) turns it on; empty means nothing is queued or sent. Panics (a recoverer that replaces chi's) and ERROR-level log lines are reported with the scrubbed message (emails, tokens, secrets, query strings and 6+ digit numbers removed), our own stack frames and the route *pattern*; never the URL, headers, body, IP, user id or cookies. Sending is asynchronous with a 50-event queue (a full queue drops), identical errors are sent once a minute, and at most 30 events a minute leave the process, so a collector outage or an error storm cannot slow or flood the API.
141. **Partner payouts are a ledger, not a money transfer.** Staff press "settle" for a partner and the app sums every completed, fully paid, not-yet-settled booking (paid minus commission), records one payout with a method and a unique transfer reference, and stamps those bookings in the same transaction (rows locked), so two staff clicking together settle once, a booking is never paid out twice and a reference cannot be reused. Moving the money stays outside the app (bank transfer, later Stripe Connect); `stripe_connect` is a recorded method only. A booking already paid out can no longer be refunded through the app (the money would have to be recovered from the partner first). Partners see their payout history and "waiting to be paid out" in the portal's Earnings tab.
142. **The old ID "verification" endpoint is gone because it verified anyone.** `POST /auth/verification` ran a stub that accepted every upload and set the ID-verified timestamp, so uploading two random files produced a "verified" flag. It is removed; the only way to become ID verified is the human-reviewed check below.
143. **F1.19 is a human-reviewed ID check, not an automated one.** A member asks for a check and gets a random 4-digit code (valid 30 minutes, one open check at a time, three rejections a day at most). They photograph an ID document and a selfie holding a paper with the code. A moderator sees the pair with the member's declared birth date, compares faces, code and date of birth, and approves or rejects with a fixed reason (code missing, faces differ, unreadable, under 18, not a valid document, other). Approval sets the existing ID-verified flag. It is honest about what it is: a reviewer comparing two photos stops casual impersonation and a minor using a parent's ID, but it is not forensic document checking, it does not scale like a paid provider, and it cannot detect a good forgery. A provider can replace it later behind the same endpoints.
144. **ID photos live only while a check is open.** They go to a private store (never a public URL), are checked against the known-abuse hash scanner before they are stored (the stub in development; production still refuses to start without a real CSAM provider), can be read only by moderators and admins through an endpoint that writes an audit entry first (no entry, no image) and never caches, and are deleted the moment a decision is made. Unreviewed checks expire after 7 days and their images are removed by a sweeper that also retries failed deletions; erasing an account deletes any stored images. Nobody can review or view their own document. Only the decision, who made it and when remain.
145. **Sponsored placements now have an admin screen.** Admins create, pause and resume placements, and see impressions and clicks, from the moderation dashboard's Sponsors tab (admins only). Ad text is shown with textContent like everything else in the dashboard.
146. **A violence model joins the nudity model, but it can only ask for a human, never block.** `hosamEl1/vit-base-violence-detection` (Apache-2.0, a ViT-B/16 trained on staged "real life violence situations") is converted to ONNX and loaded with `VIOLENCE_MODEL_PATH`; the service runs both models and merges their scores. A violence score of 0.7 or more sends an image to the review queue; blocking on violence is off (`VIOLENCE_BLOCK=1.01`) because this kind of model fires on sport, costumes and film stills, and the training data is staged fights rather than the photos members upload. Accuracy on real member photos is unmeasured.
147. **The conversion was checked, because it nearly produced a random model.** This checkpoint uses timm weight names, so loading it with the Hugging Face library silently left every weight random; a parity check (ONNX versus PyTorch logits) caught it. `tools/export_violence_onnx.py` loads it with timm, refuses to continue unless every weight matched, and refuses to write the file unless the ONNX reproduces the PyTorch output (it does, to 2e-6). The class order is not documented by the author. Ten ordinary photos all scored strongly on class 0, which fits "class 0 = non-violent" (the default), but no violent image was tested, so the order is supported rather than proven; `tools/check_violence_labels.py` lets an operator check it with their own photos.
148. **Group Would you rather is the group game.** In a matched group chat any member starts a round (a curated A/B question, never one of the last twelve in that chat), every member of either group votes once (a vote cannot be changed), and totals appear after you vote or when the round ends (everyone voted, or ten minutes). Only totals are stored and shown: no field says who chose what, and the rounds disappear with the group match. One round runs at a time so one person cannot skip past the others' votes. Group Truth or Dare stays out: its answers need a turn order across up to twelve people and a moderation story for dares in a mixed crowd.
149. **Profiles are now rich, and what anonymous modes show is decided field by field.** Members can set a relationship goal, kids, drinking, smoking, exercise, pets, languages, height, job title, education, hometown and star sign, and answer up to three prompts from a curated list of 24. The rule for Incognito and Hotel mode: answers that say *what someone wants or how they live* (goal, kids, drinking, smoking, exercise, pets, languages) stay on anonymous cards, because they are what makes anonymous matching worth doing and they identify nobody; answers that could point to a person (height, job, education, hometown, star sign) and every free-text prompt answer appear only on profiles that are visible in full. All of it goes through the one `PublicProfile` projection, and a test fixes the rule: an incognito profile never contains the job, hometown, height, education, star sign or any prompt answer.
150. **What we chose not to collect.** Religion, politics, and health are not asked for, and nor are employer or school names. They are special-category or highly identifying data that add legal weight and little matching value in a first version. Orientation stays at the existing "looking for" field. If a market expects them, they can be added behind the same projection rule.
151. **Discovery can be filtered by what people want, but not by things that pinpoint someone.** Filters: relationship goal, kids, smoking, drinking, exercise, a language, and "ID verified only". They use only the answers anonymous profiles already show. Height is deliberately not filterable (a narrow range would let someone find one particular person). The filter button shows how many are on.
152. **Match scores now weigh what people want.** The score is 30% interests, 15% age, 30% lifestyle (goal 40%, kids 25%, smoking 15%, drinking 10%, exercise 10% of that share, over the answers both people gave), 10% schedule, 15% conversation, replacing the original 40/20/20/20 split. Wanting the same thing out of dating predicts a good match better than overlapping active hours, which are rarely known, and it is information members give us directly. Missing answers are neutral and never claimed as a reason; new reasons are "You are both looking for a long-term relationship" and "Your lifestyles line up". A kids mismatch (wants versus does not want) scores zero on that answer. The change is a product judgement, not measured against outcomes.
153. **Profile completeness is a nudge, not a gate.** `GET /users/me` returns a percentage and the next missing steps (photo, three photos, intro, bio, interests, goal, lifestyle, prompts, location, ID); the app shows one card with the next step and hides it when the profile is complete. Nothing is blocked while incomplete.
154. **The swipe deck is a real swipe deck.** Until now Discover showed one small card with buttons; nothing could be swiped. It is now photo-first: the photo fills the card, name, age, verified tick and a few facts sit on a dark fade, tapping the edges flips through photos (segment bars show where you are), tapping the middle opens the full profile in a sheet, and the card can be dragged: right likes, left passes, up super likes, with LIKE / NOPE / SUPER LIKE stamps and a springy return. The same actions work from the buttons and the arrow keys. A swipe the server refuses (daily limit, no coins) springs the card back and offers the plans instead of losing the person. The old card layout remains for the Nearby and Likes-you lists.
155. **A match is a moment, not a dialog.** A full-screen "It's a match!" with the other person's photo (only when the server allowed one; anonymous matches show the veil and say they can reveal whenever they both want), "Say hi" straight into the chat, or keep swiping.
156. **Rewind undoes a pass, nothing else, and is a Gold perk.** `POST /matching/rewind` deletes the member's most recent swipe if it was a pass made in the last ten minutes, so the person can come back. Likes and super likes are never undone: they may already have created a match or told someone, and taking them back would be worse than the mistake. The app only offers rewind for passes made in this session with no like since, and says "Nothing to rewind" otherwise without asking the server.
157. **A like can carry a one-line note.** Up to 140 characters, one line, screened like a bio, only on a like or super like. It is stored in plain text next to the swipe (there is no match yet to hold an encrypted message), shown to the person who was liked next to the sender's card in Likes you, and after a match under "How it started" at the top of the chat, apart from the encrypted conversation. Sending a note is optional; from the profile sheet, "Say something with your like".
158. **A note is shown only when its sender is visible in full.** Free text is the easiest way to unmask an anonymous member ("I saw you at the bar on Friday"). If the sender is in Incognito or Hotel mode as the viewer sees them, their note is stored but not delivered anywhere: not in Likes you, not in the swipe result, not in the match list. Tested.
159. **Top picks are ranked by what two people have in common, in plain sight.** `GET /matching/top-picks` takes the same people discovery would show (nearby, visible, not swiped, not blocked), scores them on shared interests and on agreeing about what each wants (goal most, then kids, smoking, drinking, exercise; a small bonus for an ID-verified member), and returns the best three (Gold: ten) each with one sentence saying why ("You both like jazz", "You are both looking for a long-term relationship"). It deliberately does not call the AI service, so it still works when that is down, and nothing is hidden: the reason shown is the reason used. Ties go to the nearer person.
160. **Phone-size screenshots are part of how the UI is checked.** `ops/dev/phone-shots/shoot.mjs` drives headless Chrome at 390x844 against the web build, with a persistent profile so a signed-in session survives, and saves PNGs; `ops/dev/seed_demo_photos.py` gives the demo people generated sample photos. Widget tests prove behaviour; screenshots catch what tests cannot (for example the floating navigation bar covering the bottom of every sheet, found and fixed this way by showing sheets on the root navigator).
161. **Replies, reactions and unsend live inside the encrypted payload.** A reply carries the target's id and an 80-character quote, so it reads on its own even if the original is not loaded. A reaction (six quick emoji, or a double-tap heart) and an unsend notice are *control messages*: ordinary encrypted messages whose payload says "react to X" or "X was unsent". The server cannot tell them from text. The app never draws them as bubbles; it applies them in order when building the visible chat: one reaction per person per message (the same emoji again takes it back), and an unsend notice only counts when it comes from the sender of the message it names, so nobody can make the other person's words disappear.
162. **Unsend is real deletion on the server.** `DELETE /chat/matches/{id}/messages/{mid}` removes one of the caller's own messages and its attachment for everyone (the other person's app is also told, so it vanishes at once; if that notice is lost, their next sync drops it). Only the sender can; the recipient or a stranger gets 404. Messages already read or screenshotted elsewhere cannot be taken back, and the interface does not claim otherwise ("Unsend for everyone" only, no "delete forever" promise).
163. **The chat groups messages by day** ("Today", "Yesterday", a date) and long-press opens one menu: react, reply, copy, unsend.
164. **Message search runs on the device, because it has to.** Chats are end-to-end encrypted, so the server holds nothing it could search. The app searches the messages it has already decrypted and cached: case- and accent-insensitive ("cafe" finds "Café"), in all chats from the chat list or in one chat from its menu, with the match highlighted. Opening a result scrolls to that message and highlights it. Unsent messages, photos and control messages are skipped, and **disappearing messages are never searchable** (the cache cannot tell whether they have burned). The screen says plainly that it only looks at messages already on this device; a message you have never opened on this device cannot be found.
165. **GIFs go through our server so the GIF service never learns who searches for what.** The app asks `GET /gifs/search`, the server asks the provider, and the chosen GIF is downloaded through `GET /gifs/{id}` and sent as an ordinary encrypted image attachment: the other person's app never contacts the provider. Searches are limited to 40 characters and 60 a minute, and nothing is logged. Providers: **builtin** (the default): 14 animated stickers the server draws itself (hearts, stars, confetti, simple faces), searchable by a few words, no account or key, offline, nothing unexpected possible; **tenor** (`GIF_PROVIDER=tenor`, `TENOR_API_KEY`): the member's words go to Tenor from this server with a fixed client key and the strictest content filter; **none**.
166. **The Tenor adapter cannot be turned into a way to reach our network.** The media address Tenor returns is fetched only over https from Tenor's own hosts, only as a GIF under 3 MB; anything else (for example an internal metadata address) is refused. Tested against a stand-in server; never run against the real Tenor, so its response shape is taken from its public documentation.

167. **Levels are derived from the gift ledgers and never stored.** Two ladders of 30 levels each: Charm (coins received as gifts: the host's share of live gifts plus gifts sent in chat) and Supporter (coins sent). The curve is `30n² + 70n` coins to reach level n+1, so level 2 needs 100 coins, level 8 about 2,000 and level 30 about 28,000. They are computed on demand by two SQL functions (`charm_coins`, `support_coins`), so a level can never disagree with the ledger and a refund or erase corrects it by itself. Bands: Newcomer, Rising (5), Bright (10), Shining (15), Radiant (20), Legend (25).
168. **What a level shows is the member's choice, and nobody else ever sees a coin amount.** Charm is on by default and appears as a small "Lv N" badge on profiles shown in full (level 2 and up; level 1 is not worth a badge). Supporter is off by default, because how much someone has spent is theirs to share. Other people see only a level number, its band name and a gift count; the caller alone sees their own totals and progress. Anonymous (Incognito, Hotel) profiles never carry a badge, so a level cannot link an anonymous card to a live host.
169. **Leaderboards list only people who are visible, verified and opted in.** Top hosts (gift value received in live rooms) and Top supporters (gifts sent), for the week, the month or all time. A person appears only if they are in Open mode, not invisible, verified, not banned, have the matching level switched on, and have no block with the viewer in either direction. Entries carry rank, name, level and gift count; the viewer's own rank is returned even when outside the top 20.
170. **Following is a one-way bookmark, only for profiles shown in full.** `POST/DELETE /follows/{ref}`, idempotent, at most 500 follows. An anonymous member can be neither followed nor listed (a follower count on an anonymous card would be a fingerprint). The count of followers is public on visible profiles; the list of who follows you is private to you. If someone later goes Incognito they drop out of every follow list without being unfollowed. A block in either direction deletes the follow and prevents a new one.
171. **A followed host going live sends one generic push.** "Someone you follow is live" carries no name, title or room detail (only the room id for opening it), is collapsed per room, and has its own notification switch (`live`, default on). Older apps that do not know the switch cannot turn it off by omission: a prefs update keeps any field it leaves out. Rooms you follow sort first in the live list and are flagged; the list can be narrowed to followed hosts.
172. **Live rooms have topics and a pinned line.** Seven topics (chat, music, talent, gaming, dating, wellness, learning); the host picks one when starting and the list can be filtered by it. The host can pin one line (120 characters, screened like chat) that every viewer sees at the top of the room and in the list; an empty line clears it. Viewers learn about changes from the same events poll they already run, so no new connection is needed.
173. **Comments on posts follow the post's visibility, not their own.** Anyone who can see a moment, Little Universe or community post can comment; nobody else can read or write, and a block hides each other's comments. Under an anonymous (Universe) post everyone, the author included, is a nickname that is stable inside that post and different on every other, derived from a hash so it needs no storage and cannot be linked across posts. Under a moment or community post a commenter is named only if their profile is shown in full; otherwise they are "Someone". No photos in comments. Missed connections have no comments (they are deliberately one-to-one). 280 characters, screened like posts, 100 comments a day each, 300 per post; comments are deleted with their post, by their author, or by the post's author; any comment can be reported with its text as evidence.
174. **Quiz-first matching: a percentage, never the answers.** Members answer any of 30 curated multiple-choice questions about daily life and values (stored privately, changeable, removable). Between two people the quiz match is the share of questions both answered where they picked the same option, rounded to the nearest ten, and shown only once at least 8 questions are shared. It appears on every card, anonymous ones included: that is what lets someone judge an anonymous person before any photo. No endpoint returns another person's answers, and the rounding plus the minimum stop the percentage being used to read someone's answers one at a time. A determined person could still probe by answering many questions and watching a target's percentage move; that needs an account, many answers and a target they can already see, and is accepted for a first version. It is a display, not a ranking: it does not change who is shown.
175. **Reveal happens in steps: voice first, photos later.** In an anonymous (Incognito or Hotel) match either person can offer to swap voice intros. Each side agrees on their own; the clips unlock only when both have, and the offer needs your own voice intro (it is a swap). The reply says only whether the voice is unlocked, never that the other side is waiting. Unlocking exposes the other person's voice intro and its length and nothing else: the card stays anonymous, `voice_intro_s` still never appears, and the full reveal (photos and name) is the existing second step with its own mutual consent. The audio endpoint refuses outsiders, anyone before both agreed, blocked pairs and ended matches, and is never cached. A voice is identifying to people who know the speaker; that is why it is opt-in on both sides and stays out of every list.
176. **Voice rooms have topics.** Open mic, Love and dating, Stories, Music, Advice, Night owls and Confessions; the host chooses one, the list can be filtered by it, and anonymous rooms keep their nickname rule (a host in Incognito mode is always anonymous). The topic is a label only; it changes no privacy behaviour.
177. **Quiet hours silence everything except incoming calls, and silenced pushes are dropped, not saved.** A member sets a daily window (default 22:00 to 08:00, off until switched on) and the app sends the phone's offset from UTC with it, so the server applies the window in local time and handles windows that cross midnight. A notification that arrives inside the window is not queued for later: opening the app shows everything anyway, and a queue of "you have a new message" pushes released at 08:00 would be noise. Calls are exempt because a call that rings after the caller gave up is useless. A prefs update that leaves a field out keeps its old value, so older apps cannot switch quiet hours off by accident.
178. **Onboarding is a skippable five-step welcome, shown once.** Photos, what you are looking for, a prompt, the compatibility quiz and notification choices; each button opens the real screen for it and moves on afterwards, and "Skip for now" or finishing records `onboarded_at` so it never reappears (also from another device). Everyone with a profile before this release counts as onboarded. Nothing is blocked by skipping; the completeness card keeps suggesting the next step. A weekly digest was deliberately not built: it needs an email channel and a job for little value at this stage.
179. **Co-hosts share a live room but never own it.** The host can invite up to two people who are shown in full (Open mode, verified, no block either way). A co-host gets a publish token (and is switched to publish at once if already watching), can mute and remove viewers and pin the line, and appears to viewers as "With <name>". A co-host cannot end the room, add co-hosts, or moderate the host, and the rights vanish with the room or when removed. Gift earnings stay with the host.
180. **Gifts fly.** A gift arriving in a live room animates a picture chosen from the gift name (rose, champagne, heart, star, crown, otherwise a present) rising over the video, besides the existing text toast, on both the viewer and the host screens. It is decoration only: it reads the same announcement everyone already sees.
181. **A reply to your post or short sends one generic push.** "Someone replied to your post", collapsed per post for ten minutes, never your own comment, with its own switch (`comments`, default on) and subject to quiet hours.
182. **Short videos have comments and a Following filter.** Comments on shorts follow the clip's visibility (it is only visible to people who can see its Open-mode author), name a commenter only if they are shown in full and otherwise say "Someone", are removed with the clip, by their author or by the clip's owner, and can be reported with their text. The video feed can be narrowed to people you follow, and each clip shows a comment count. The comments sheet is one shared component with the post comments.
183. **The investor page is a pledge ledger, not an offering, and it is off unless switched on.** `ENABLE_INVESTORS=true` mounts it (on locally, off in `.env.example`). Selling shares of a company to the public is regulated in nearly every country (securities, crowdfunding and consumer-protection law, often licences and disclosure documents), and doing it without that paperwork can be illegal for the company and the founder. So the app does not take money or issue shares: a signed-in, verified member records a **pledge** (US$1 to US$100,000, at most three pending), sends the money by an arrangement outside the app (`INVESTOR_PAYMENT_NOTE` plus a reference like INV-1A2B3C4D), and the owner marks it received in the admin dashboard's Investors tab (confirmation asks first and is written to the staff audit log). Only confirmed pledges count. The page says in plain words that nothing is issued until a written agreement is signed. **A lawyer must approve the wording and the process before this is switched on anywhere real.**
184. **Ownership is derived: founder 51%, investors share 49% by money.** A holder's share is 49% x (their confirmed money / all confirmed money), rounded down to six decimals (0.000001%). So the first US$49,000 at the US$1,000-per-1% starting price fills the pool exactly (US$1,000 = 1%); when another US$49,000 is confirmed the same US$1,000 becomes 0.5%; US$1 is 0.001% and US$10 is 0.01%. Percentages are never stored, so they cannot disagree with the money. Founders' 51% is fixed. Rounding down means the board can total a few millionths of a percent under 100%, never over. This is a pro-rata pool as specified; it is unlike ordinary share issuance (where existing holders are diluted by new shares at a price), and the lawyer should check that it is what the agreements will say.
185. **The public board shows names and percentages only.** `GET /investors/public` needs no account and returns the founder (Vishal Saini, 51%) first, then each investor by size, with only a name and a percentage: no amounts, emails, references or dates. An investor who unticks "Show my name" appears as "Anonymous investor" (it is their choice, per pledge, and the least-exposed one wins if they have several). Display names come from their profile.
186. **Accessibility is tested, not hoped for.** `test/contrast_test.dart` computes WCAG contrast for every text and control colour pair in both themes (4.5:1 for text, 3:1 for outlines and icons) and for the text on each visibility mode's gradient. It found and fixed real problems: the red used for errors was 3.6:1 on the dark surface (now a lighter red in dark mode), and the ends of the Open and Incognito gradients were just under 4.5:1 for their text (slightly adjusted). `test/a11y_test.dart` draws nine screens at the largest text size (2x) in both themes and fails on any layout overflow, and runs Flutter's own tap-target (48 dp) and spoken-label checks on the screens people use daily. It found and fixed: three screens that overflowed at large text, round deck buttons under 48 dp, video-feed buttons with no spoken name, and filter chips squeezed to 36 dp.
185a. **The swipe deck works without dragging.** For a screen reader the top card is read as one description (name, age, ID verified, quiz match, charm level, distance, intro) and offers Like, Pass and Super Like as actions; the keyboard arrow keys already worked. An anonymous person is read as "Anonymous".
187. **Appearance is the member's choice, kept on the device.** Settings, Appearance: theme (match the phone, light or dark), text size (Default, Large, Larger, Largest, multiplying the phone's own setting, capped so layouts hold) and reduce motion. Nothing is sent to the server; if device storage is blocked the choice simply lasts until the app closes. Reduce motion (also honoured when the phone asks for it) stops the flying gift, the floating match pulse and the springy swipe, and shortens mode changes to a single frame.
188. **Trusted contacts must agree before they are ever sent anything.** A member can name up to three people (name and email). Each gets one email with a confirmation link; until they open it nothing else is sent to them, so the feature cannot be used to mail a stranger. The link is an unguessable one-time-style token (stored only as a hash) and needs no account. A member cannot name their own address. Contacts and plans are private to the member and deleted with the account.
189. **A date plan is a promise to check in, backed by an email.** The member picks a confirmed contact, a place, a time and how long after meeting they will check in (1 to 8 hours). The contact is emailed the place and times, and the other person's name only if the member chooses to include it and that person is shown in full: an anonymous match is never named. A reminder push ("Time to check in") goes to the member 15 minutes before the deadline and is never silenced by quiet hours. If the deadline passes without a check-in the contact is emailed once, with plain advice (try to reach them; contact local emergency services if worried), and the plan is marked alerted; checking in afterwards sends an all-clear. The member can extend the deadline up to three times, or cancel (the contact is told). It is a nudge for people to look after each other, not an emergency service: the app does not call anyone, track a location or contact the police, and says so.
190. **Scam warnings are computed on the device, on the other person's messages only.** Chats are end-to-end encrypted, so the server cannot read them and is never told. After decryption the app looks at the recent messages the *other person* sent for the patterns romance scams use (asking for money, gift cards or crypto; moving to another app or a link; asking for ID or card details or an address). A match shows a dismissible banner with Report and Block, worded as "may". Nothing is blocked or sent, the check will sometimes be wrong in both directions, and a determined scammer can phrase around it. Disappearing and unsent messages are not examined.
191. **Live rooms have looks.** Six themes (plain, sunset, neon, forest, ocean, velvet) chosen by the host when going live; viewers see the room tinted and its card in the list coloured. Decoration only: a theme changes nothing about who can watch, chat or gift.
192. **A reveal can be set for a time, and needs both people.** In an anonymous match either person can suggest "reveal together in 1 hour / 24 hours / 2 days". It does nothing until the other agrees; once both have, photos and names unlock for both at that moment (the server records both consents, exactly as if each pressed Reveal), unless either person cancels first. An unanswered suggestion lapses after a day, an agreed time cannot be changed without cancelling, and a match that ended in between is skipped. A one-minute job runs it, so it can be up to half a minute late.
193. **The weekly summary is opt-in, numbers only, and one tap to stop.** Off until a member switches it on (Notifications). Once a week it emails how many people liked, matched with, followed or replied to them, never names or message text, and only if there is something to report. Every email carries a signed link that switches it off with one tap and no sign-in. The summary needs mail delivery (SMTP) and `APP_URL` to point at the web app.
194. **The app is ready for other languages, with three to start.** Strings live in translation files (`lib/l10n/*.arb`), turned into code by Flutter's generator; English, Hindi and Spanish exist. Each member picks a language (or follows the phone) in Appearance, saved on the device. Only the bottom navigation and the Appearance screen are translated so far: the pattern is proven, the rest of the app's text still has to be moved over. **The Hindi and Spanish text is a first draft by the developer and needs review by native speakers before it is shown to the public.** A test fails if a language is missing a key or a placeholder.
195. **Event groups are boards for people with a spot at the event.** Joining a partner event (free or paid) opens a "Group" button: who else is going (names only for members shown in full, up to the first 50) and a message board of up to 280-character messages, screened like other public text, 60 a day each and 500 per event. Only people with an RSVP can read or write, so leaving the event closes it for you; blocks hide each other; names appear only for Open-mode members and everyone else is "Someone". Members can delete their own messages and report others (the text goes to staff as evidence). Everything is deleted a day after the event ends or is cancelled.
196. **Sounds on short videos are deliberately not built.** Adding music to clips means licensed music (or a licensed library), per-country rights, and takedown handling; none of that exists, and offering unlicensed sound would put the company at legal risk. Members can already use their own audio inside the video they record.
197. **More of the app now speaks Hindi and Spanish.** The sign-in screen, the tagline, the Discover tabs and the main Profile menu titles join the navigation and Appearance screen. Still a first draft needing native review, and most screens are English.
198. **A second group game: Most likely to.** In a matched group chat anyone starts a round with a light prompt ("Most likely to cook a feast for everyone"), everyone in either group picks one person, and after voting each member sees how many picks each person got, never who picked whom. It shares the one-round-at-a-time rule with Would you rather (a round of either blocks the other), a vote cannot be changed, and members are shown by name only if their profile is shown in full ("Member A", "Member B" otherwise). People in the vote list are identified by their public ref, never by an internal id.
199. **Live polls are the live-room party game.** The host or a co-host asks the room one question with 2 to 4 short answers (screened like chat); viewers tap once to vote, the first vote stands, and the totals show live to everyone (it is a game for the audience), to the host straight away. One poll at a time per room; ending it keeps the result on screen for two minutes; it disappears with the room. Nothing records who chose what in any answer.
200. **Registration, password reset and the chat list now speak Hindi and Spanish.** Still first drafts needing native review; screens not yet moved to translation files stay in English.
201. **Group Truth or Dare takes turns round everyone.** In a matched group chat (and in masked rooms) players go in a fixed order; the player up picks truth or dare, gets a prompt from the same curated bank as the two-person game (light, nothing sexual, no money, no risk), then finishes or skips (two skips each). If the player up is idle for five minutes anyone else can move the game on at no cost to them, and if they leave the next player is up. Needs three players. In a group chat the answers are given in the end-to-end encrypted chat and never stored.
202. **Masked rooms are Masked Truth for three to five strangers, with weaker privacy than a chat and a clear label saying so.** Members queue; five are seated at once, three or four after the oldest has waited 20 seconds; nobody who has blocked or been blocked by someone already seated is seated with them. Everyone gets a made-up name for the room's 25 minutes (a name is never reused in a room). There is no chat and so no end-to-end encryption: a truth is answered in a short (200 character) screened text that every member sees; a dare is just marked done. Answers can be reported (staff see the prompt and the text); rooms and answers are deleted an hour after they end. Answers are server-stored text, which is why the screen says "not end-to-end encrypted".
203. **Short videos can carry a sound, from a library the server composes itself.** Eight short loops (warm, upbeat, calm, night, dreamy, fun, romantic, energetic) are synthesised from a few notes and a drum pattern, so there is no recording, sample or third party behind any of them: nothing to license or be taken down. They are loops to sit under a clip, not songs. The app plays the loop alongside the clip (mute button in the feed); the sound is not mixed into the video file, so anyone saving the clip gets the clip without it. Replaces decision 196's "not built" with a licence-free version; commercial music is still out.
204. **Much more of the app is translated.** About 190 common labels and buttons (cancel, report, follow, start, done and so on) across most screens now have Hindi and Spanish text, inserted by a scripted pass that left any spot untouched where it would not compile. Still drafts needing native review; sentences and messages with changing parts (counts, names, times) are still English.
205. **Screens that were polled every 2-3 seconds now get a "something changed" signal, and keep polling as a slow backup.** The Go API publishes `sig:<kind>:<id>` on Redis after any successful write to a live room, a game, a masked room or an event board (one middleware, path-based; a viewer joining a live room is deliberately not a signal, so a big room does not wake itself up on every arrival). The Node relay forwards it to sockets that asked to `watch` that topic, at most one signal per topic every 400 ms. A signal carries no data, only a topic: the screen refetches through the normal, authorised API, so nothing new can leak. Watching is authorised by a new `GET /signal/{kind}/{id}/access` (members of the game or masked room, anyone with a spot at the event, any live room). In the app, `LiveRefresh` polls at the old rate until the relay accepts the watch, then at one tenth of it; if the relay is down or refuses, the old fast polling simply continues. Not covered: 1:1 quiz (its id is not the match id) and the call/random-chat screens still poll.
206. **Leaderboards are computed once and reused for 30 seconds; blocks are never cached.** The ranking (top 200, summed from every gift) is the expensive part, so it is cached per board and period, shared by all viewers. What each viewer may see (blocked in either direction) and their own rank are applied fresh on every request. `levels.CacheTTL` is zero in tests.
207. **Scam warnings read Spanish and Hindi, in Devanagari and in the Latin spelling people type (`paisa`, `udhaar`).** Still keyword lists: they miss some scams and flag some innocent messages, so the wording stays "may". A smarter check by the AI service was not built.
208. **A member can change or remove at most 6 existing quiz answers a day.** Without a cap someone could flip one answer at a time and watch another person's match percentage move, which reads that person's private answers off the number. First answers to a question are free, saving the same answer is not a change. Counted in `compat_changes`; the 7th gets 429 and nothing is saved.
209. **Masked rooms have a cooldown and keep evidence.** Leaving a room and queueing again within two minutes is refused (429); someone reported by two different people within a day cannot join new masked rooms for that day. A report now stores the reported line **and the room's last 30 lines under their made-up names**, because the room is deleted an hour after it ends and the moderator needs context. Staff see these as ordinary reports; there is no separate "room" screen.
210. **Check-in alerts go to every confirmed contact, not only the one on the plan.** A contact who does not read their email in time must not be the only safety net; the plan's own contact is mailed first, unconfirmed addresses never. If the member then checks in, everyone who was alerted gets the all-clear. SMS was not added: sending texts to numbers nobody confirmed is a consent problem, and needs a provider and number verification first.
211. **Photos can be reordered, captioned and one made main.** The first photo is the main one (shown on cards). A caption is up to 100 characters, screened like a bio, and shown only to people who may see the photo itself (never in Incognito or Hotel mode). Edits lock the photo list so two edits cannot overwrite each other.
212. **The investor page has a second model: fixed price per percent.** `INVESTOR_MODEL=fixed` (and `INVESTOR_PRICE_PER_PERCENT`, default 1000) makes $1,000 buy 1% and keep it; nobody is diluted and the 49% sells out at $49,000 (a pledge over what is left is refused, and a confirmation that would overfill is refused). `prorata` stays the default and is what the owner asked for: it dilutes everyone as money arrives, which is unusual and is stated in the notice. Which one to use is a legal and commercial decision for a lawyer; the app shows the right notice for either. Still a ledger, not a share register.
213. **Live hosts can ask to be paid, and staff record the transfer.** A host with a verified ID and at least 5,000 coins of unpaid gift earnings asks for a payout; every gift is stamped with that payout so it cannot be paid twice; a rejection frees the gifts; staff (admin) record amount, method and a transfer reference, which can be used once. The app moves no money. The conversion from coins to dollars is chosen by whoever pays, because the rate is a business decision, not code. Deleting an account deletes its payout history: whether financial records must be kept is for a lawyer.
214. **The staff dashboard shows trends and can find members by name.** A funnel (signed up, confirmed email, finished welcome, added a photo, started swiping, got a match; each step counts only people who also did the steps before), a per-day chart (sign-ups, swipes, matches, reports, live rooms) and the reasons people report, for 7, 30 or 90 days; aggregates only. Member search matches the start of a display name or an exact profile code, shows no email, birth date or location, and every search is written to the audit log.
215. **Match-score weights can be tuned from real outcomes without a code change.** `SCORE_WEIGHTS` (JSON, all five parts, non-negative, summing to 1) overrides the defaults; anything else is ignored with a warning. `ai-service/tools/tune_weights.py` reads past matches with a good/bad outcome and reports how well each part separates them (AUC) and a suggested set. It needs hundreds of real matches to mean anything and says so; the defaults are unchanged because there is no real data yet.
216. **Backups are proven by restoring them.** `ops/backup/drill.sh` dumps Postgres and Mongo and archives media, restores them into scratch copies (never touching live data) and compares row and document counts, applied migrations, the spatial index and every media checksum. It passed on the local stack. It does not test point-in-time recovery, restoring to a different machine, or re-applying erasures made after the backup (see RUNBOOK), which are the drills still owed.
217. **The bottom bar shows a word under each icon.** The word is held to a small size so a large system text setting cannot break the bar.
218. **Staff see masked-room reports together, and banned members can appeal.** Reports about a masked room now carry the room's id, so the staff dashboard has a "Reported rooms" tab: one card per room with how many people reported it, why, and the reported line plus the room's last lines under their made-up names. A banned member cannot sign in, so `POST /moderation/appeals` is public and proves the account is theirs with its email and password; every way it can fail (unknown email, wrong password, not banned) gets the same refusal, so it cannot be used to find out who has an account. One open appeal per member, five tries an hour per IP. Staff with ban rights lift the ban (the normal unban, same audit entry) or keep it, and write the reason; the staff view shows the display name and profile code, never the email. The member is not messaged: they find out by signing in.
219. **A member can ask the AI to look closer at a chat, one time, by choosing to.** The scam banner (which still runs on the phone) gets a "Look closer" button. It says plainly that the last eight text messages will be sent once, not stored, and nothing else from the chat. The AI service reads only what the other person wrote and looks at the combination: love declared early, a story about why they cannot meet or call, urgency, secrecy, leaving the app, then money, crypto or documents; English, Spanish and Hindi. It answers low, medium or high with the reasons and what to do. It is rules, not a language model, so it is explainable, free to run and fully testable, and it is a guide that will miss some scams and flag some honest people. Never blocks anything; nobody else is told.
220. **Trusted contacts can be reached by text message too, but only after they read a code to the member.** Adding a number texts it a six-digit code; the member must type the code the contact reads out, so the number's owner has agreed. Three codes a day per contact, five wrong tries voids a code, a code lasts 15 minutes. A confirmed number gets the same missed-check-in alert and the all-clear as the email. The list shows the number masked (last two digits). Twilio is the provider (`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`); in development texts are written to the log; in production with no provider the feature says it is unavailable rather than pretending.
221. **A reporter can see what became of their report, but never who it was about.** `GET /moderation/reports/mine` lists the caller's own reports (reason, date) with one of three outcomes: waiting, action taken, or no action. It never includes the reported member, their name, or what the action was, so it cannot be used to find out whether someone was banned. Reached from the Safety center. No push yet: the list is read when the member opens it.
